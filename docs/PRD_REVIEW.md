# App review against PRD v0.8

26/09/2026 · Updated through branch `codex/operator-export-restore` and its preceding stacked feature branches. Fresh GitHub checks found the current branches aligned with their remotes. The implemented increments are not in production. Production activation evidence comes from HANDOVER.md and the earlier live verification, not a new live-service audit in this review.

## Assessment

The app is a persisted web foundation with dog profiles, invitation and activity approval, explicit staff assignment, configurable venue inventory, a conflict-safe grooming booking and visit slice, staff-assisted admission with configured capacity, a membership entitlement model, and a Stripe sandbox Checkout/webhook contract. It is not yet the operational payment and café product specified for the pilot. Stage 1 remains incomplete; Stages 2 and 3 have partial web implementation. A successful deployment and attractive login do not satisfy the launch gates. No percentage is assigned: requirements differ greatly in size and operational importance.

Basis: PRD.md v0.8, ROADMAP.md v0.8, WHITE_LABEL_PLATFORM.md, application routes/components/domain code, migrations, test inventory, local browser acceptance and handover. This is a requirements/code review, not a full security or native-device audit. All 98 tests and the TypeScript check pass in the embedded harness and against disposable PostgreSQL 17; browser acceptance covers operator/member/staff invitation onboarding, staff assignment and qualification, location-aware booking setup, grooming approval, staffing-aware booking/cancellation, one grooming visit through verified collection and correction, a manager-to-member demo membership journey, applying/restoring a grooming credit, staff-assisted admission through checkout, household-adult permissions, lifecycle controls and the authenticated operator export. Automated tests cover the Resend recovery request contract and signed Stripe event normalisation/reconciliation, but no real Resend inbox, Stripe account, hosted Checkout or provider webhook has been exercised yet. It does not prove live email delivery, payment collection, complete workforce operations or production rollout.

## Highest-priority gaps

1. **Onboarding, booking and grooming visits work locally and pass against disposable PostgreSQL 17, but are not production-ready.** A new operator and member can join, create a dog, complete grooming approval, reserve a staffed slot and progress it through verified collection without database setup. Independent account-creation email verification, a real sender-domain/inbox recovery rehearsal, wider care/documents, managed staging/ledger rehearsal, public acceptance throttling and payments remain before rollout.
2. **Care and social data need separate workflows.** Preserve the existing public allowlist while extending private structured care fields/documents and activity eligibility. Household assistance now follows explicit grants and does not turn the public bio into a substitute care record.
3. **Community launch needs moderation and lifecycle controls.** Unpublishing works, but reports/blocks and membership-ending behaviour are absent. Keep the pilot closed until those PRD P0 controls are in place.
4. **The minimum staffing dependency is now configurable and enforced.** Managers can securely invite, appoint and qualify a groomer, delegate inventory setup and deactivate access; booking requires an active qualified groomer on a published location-matched shift and respects its break. Complete invitation delivery, reception/care permissions, recurring patterns, leave/sickness/swaps, coverage warnings and staff self-service before treating AD-02 or the PRD rota capability as complete.
5. **Production identity now has a code boundary but still needs rollout proof.** Production runtime hides demo labels, synthetic credentials and demo manager defaults. Deploy and inspect that presentation, configure and test the recovery sender, add staff MFA, resolve the recorded database privilege warning and verify credential rotation before real customers.
6. **Native apps remain a launch obligation.** Start the shared mobile foundation alongside backend contract stabilisation, not after declaring the web product complete.

## Recommended next delivery sequence

This is a proposed refinement, not an approved reduction in PRD scope.

1. Finish foundation proof: deploy and verify the production/demo boundary, exercise recovery through a verified sender and real test inbox, compare/rehearse the historic ledger in managed staging, and preserve the proven two-operator setup and platform-owned export/restore checks.
2. Complete dog/community slice: private care capture and approval, gallery/audience preview/search, moderation/blocking, membership expiry policy; start iOS/Android sign-in/profile/photo path against shared domain contracts.
3. Extend the proven local journey in a test environment: add admission document/exception policies, booking policy windows, rescheduling and part-credit/cash rules around the now-connected entitlement ledger. Connect a real ready-notification route only after communication consent, delivery and fallback rules are agreed.
4. Prove commerce against a real Stripe test connected account and CLI-delivered webhooks, then add Customer Portal, deposits/balances and café sale/refund reconciliation. Keep operator software billing separate and choose one supported counter route.
5. Complete workforce/integrations: rotas/leave/swaps/coverage, actual clocking, approved timesheets, first validated payroll route, then second-adapter evidence before claiming interchangeable providers.
6. Pilot gate: native device/store readiness, complete member journey and staff shift rehearsal, financial reconciliation, notifications, privacy/export/deletion, recovery, accessibility and operator sign-off.

## Decisions to obtain before booking/payment build

Membership unit and tiers/prices; real operator name/address; staffing and independent-groomer model; service durations/buffers/resources/opening hours; admission/documents/cancellation rules; payroll and POS edition/hardware; shared app versus separately branded store distribution. These affect behaviour and cannot safely be replaced by guessed production defaults.

## Conclusion

Ready to demonstrate the visual identity, profiles, audience controls, operator/member invitation onboarding, staff roles with bounded delegated administration, configurable venue inventory, hashed one-time account recovery with manual fallback and a production email adapter, explicit household-adult dog-care and booking permissions, separate grooming and club-admission decisions, conflict-safe booking, whole-credit redemption/restoration, staff-assisted capacity-controlled admission, the booked grooming visit through verified collection, and transparent demo memberships with an auditable ledger. Production runtime removes synthetic presentation, and the Stripe sandbox code contract connects hosted subscription Checkout events to the entitlement model. Neither Resend nor Stripe has been exercised with real test credentials. Not ready for a paid operational pilot or a claim of complete white-label onboarding. The next foundation milestone should prove two fresh operator setups and the migration stack without SQL; the next commerce milestone is a real test-account walkthrough with signed CLI webhooks.
